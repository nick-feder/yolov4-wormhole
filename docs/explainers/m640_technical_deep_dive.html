2. The whole journey: from baseline to m640

This project did not start with custom kernels. We first measured the end-to-end submission, identified where time and accuracy were being lost, fixed the highest-impact causes, and only then built device kernels and chose the operating point. Each phase changed what the next phase needed to optimize.

PhaseWhat we found or changedMeasured milestoneWhy that led to the next step
0. Establish a real baseline The unoptimized submission launched a large graph of individual operations and spent substantial time in the host path. We recorded both the plain reference and the organisers' traced fast reference. Plain reference: 85.3 ms/photo; fast reference: 17.8 ms/photo and .464 practice mAP@50. Tracing removed much of the Python launch overhead, but the remaining 17.8 ms still included avoidable input, output and graph work.
1. Keep the card fed Moved decode/resize and tensor preparation into parallel workers, limited nested PyTorch threading, and overlapped output processing with the next card pass. Input-path stage: 17.6 → 12.9 ms/frame; input plus overlapped output reached 5.9 ms/frame in an early pipeline measurement. Those changes exposed the next bottlenecks: box decoding and many small card operations. These are stage measurements, not directly comparable final m640 benchmarks.
2. Recover accuracy before chasing more speed The card was .094 below the fp32 CPU reference. Higher HiFi modes did not fix it. Inspection found HardMish substituted for Mish in 72 locations; replacing the approximation with real Mish restored the activation the weights were trained for. At 320, library Mish raised practice mAP from .464 to .5145, costing about 0.7 ms. Real Mish, fp32 accumulation and multi-label NMS brought a later 320 card pipeline to .5662, matching the .5667 fp32 CPU ceiling with multi-label. Accuracy was no longer the reason to avoid the card. The extra cost of faithful Mish became a prime target for a custom SFPU implementation.
3. Move box generation out of the card's small-op tail Replaced slow framework-heavy NMS operations with a faster exact path; enabled multi-label detections; then stopped the card after raw detector heads and decoded them on the host using compiled code. Raw-head change: 5.95 → 3.74 ms/frame in the earlier pipeline. The exact box step dropped from 7.30 to 4.05 ms on one core (identical detections), and to 3.35 ms in the later offline benchmark; torchvision batched NMS then reached 1.38 ms at the same mAP. Multi-label added about +.022 mAP at the same speed. Even after host and output improvements, the model graph had a high fixed cost per pass. The next large lever was to process more source photos per pass.
4. Expand the speed/accuracy frontier—and debug 640 Built resolution variants and tested mosaics. The first 640 path produced bad features because a neck convolution read a mismatched shard layout: the 320-only branch explicitly resharded its input, while the larger-resolution branch skipped that step. We enabled resharding above 320 (reshard_if_not_optimal = resolution > 320) and rechecked the stages. Mo's hardware report also notes that 16-bit accumulation degraded 640 output (PCC 0.768) and that fp32 accumulation fixed it. The pre-fix 4 × 320 mosaic measured about 3.97 ms/photo but only .4447 mAP. After fixing the layout and searching 28 graph/precision settings, the no-kernel m640 point reached 2.755 ms and .5581 practice mAP (2.389 ms / .6392 on COCO1k in that matrix). The layout issue showed that a fast result is meaningless if tensor placement is wrong. After the fix, m640 became a valid accuracy/speed knee and the target for kernel work.
5. Replace the remaining costly device patterns Implemented four kernels: a faster Mish SFPU path; Mish plus residual addition; an SPP max-pool kernel; and a sharding-aware upsample/concat kernel. Also removed unnecessary moves/conversions and overlapped output transfer using a second command queue. In the 320 kernel-stack comparison, 3.924 → 3.342 ms/frame in the same job. After porting to all six configurations, the stack reduced COCO1k time by about 24–30%, depending on the point. We generalized kernels only after establishing the Pareto configurations. That avoided optimizing a single input size that the final system would not use.
6. Improve ranking and validate the combination Added box-step v2: object/class score re-ranking, fused box voting and a mosaic tile-edge penalty. Then measured it together with the custom kernels rather than assuming independent gains would stack. Across six COCO1k configurations, v2 improved mAP by +.0037 on average (held-out half: +.0034 average, positive on all six). The m640 kernel+v2 cross-check measured 1.672 ms / .6439 mAP on COCO1k. The combination check established the submitted stack and gave us evidence for both runtime and accuracy without relying on separate ablations.
7. Select m640 for the scored run Compared the fastest mosaic against the larger-margin m640 point, the single-image resolutions, and the scoring rules. Selected m640 with kernels + v2: 2.106 ms/photo and .5586 practice mAP. Against 17.8 ms / .464, that is about 8.45× faster and +.0946 mAP. m512 is faster but has a narrower accuracy margin. m640 sacrifices some speed to keep a much larger buffer above the score's .447 accuracy floor.
Do not sum the phase timings. The 12.9, 5.9, 3.74 and 3.35 ms figures come from different stages and test setups; some optimizations overlap. The defensible end-to-end comparison is the same-set reference versus the selected m640 run, with intermediate numbers used to explain how the bottlenecks changed.

The rest of this document unpacks the final m640 architecture and explains the mechanisms behind each phase.

3. End-to-end architecture

The model remains YOLOv4: the work was in restoring its intended behavior, selecting an efficient input/execution mode, reducing framework overhead, and replacing expensive operations with targeted kernels. The weights and YOLO architecture were not replaced with a different detector.

4. Why the selected configuration is m640

m640 is a four-image mosaic using 320-pixel tiles. It is not four native 640 × 640 inferences and does not give each photo 640-pixel detail. Each source photo is resized to 320 × 320, then placed in one quadrant of a 640 × 640 canvas.

photo A ┌──────────┬──────────┐ photo B
        │ 320×320  │ 320×320  │
        ├──────────┼──────────┤
photo C │ 320×320  │ 320×320  │ photo D
        └──────────┴──────────┘
             one 640×640 model pass

The card's graph has a mostly fixed cost per pass: launching and scheduling hundreds of operations costs time even when each operation does little arithmetic. Four photos in one pass amortize much of that fixed cost. The model still processes the pixel work for all four tiles, but the per-pass overhead is shared.

Correctly recovering each photo's boxes

  1. Resize each input photo to its 320 × 320 tile and place it in the 2 × 2 canvas.
  2. Run the 640 × 640 YOLO graph once.
  3. For each predicted box, use the grid cell that produced it to identify its tile. The implementation groups that tile's cells back into the normal per-image head layout.
  4. Decode and rescale each tile's boxes in its own 320 × 320 coordinate system, then map them to the original photo dimensions.
  5. Apply a small confidence penalty to boxes near internal tile edges, where an object may be cut by the mosaic boundary.

Because each prediction belongs to the cell that emitted it, tile ownership can be recovered from the head-grid location rather than guessing from the final box center. This matters when predicted boxes extend beyond a tile boundary.

5. How the accelerator runs it

The Wormhole n150 provides an 8 × 8 grid of 64 Tensix cores. Each core has local SRAM (L1), data-movement engines, and separate matrix and vector math units. The host CPU prepares work and orchestrates the device; it does not replace the card's neural-network computation.

Host / PCIePrepare input tensors and schedule the graph.
→
NoC + L1Move and stage sharded tiles in each core's local memory.
→
UnpackConvert stored tile data into register operands.
→
FPU / SFPUMatrix products and vector operations update destination registers.
→
Pack + NoCWrite results to L1 and route them onward or back to the host.
  • FPU: the matrix engine used for convolution/matmul work and additions.
  • SFPU: the vector unit used for elementwise functions such as Mish and max operations.
  • Unpacker and packer: move between L1 tile formats and registers. Tile data is distributed across cores, so layout and sharding determine whether an operation can avoid copies.
  • Command queues and traces: record/replay the model work and overlap transfers with computation where dependencies permit.
Important K2 detail: its SFPU Mish and FPU residual addition are issued back-to-back in the compute instruction stream. We fuse the dataflow and reuse the destination registers; we do not claim that SFPU and FPU execute the same element simultaneously.

7. Accuracy recovery: restore the model's intended activation

The card port initially scored .464 mAP@50, while the same weights in an fp32 CPU reference scored .558. Increasing precision did not fix the gap: bf16 weights with HiFi4 scored .445, no better than the .464 LoFi baseline. The investigation found that the port had substituted HardMish for the YOLOv4 model's Mish activation in 72 locations.

FunctionDefinitionBehavior that matters
Mishx · tanh(ln(1 + e^x))Smooth; retains small negative outputs for negative inputs.
HardMishx · clamp(x + 2, 0, 2) / 2Cheaper piecewise approximation; differs most in common activation ranges and cuts off negative tails.

Replacing Mish with HardMish in the fp32 reference reproduced most of the observed accuracy loss (.558 → .479, versus .464 on the card). Restoring real Mish on the card improved the 320 practice result from .464 to .5145 (about +.05 mAP), at roughly +0.7 ms for the library implementation. That accuracy fix motivated the custom Mish kernel, which made the more faithful activation much cheaper.

Precision was treated as a measured knob, not a blanket fix

  • Fp32 accumulation helped at 320 (+.024 mAP for about +0.22 ms) but did not consistently help the larger or mosaic graphs; the selected m640 uses ACC=0.
  • The first convolution is a targeted exception: PREC_FIRST=1 applies bf16 with HiFi4 and fp32 accumulation. It is a small portion of the graph and measured as beneficial or neutral in 13 of 14 comparisons.
  • Using bf16 activations everywhere at 320 crashed the graph. Precision changes therefore remained constrained by the graph's supported layouts and types.

8. Detection heads and box processing

Return raw heads instead of hundreds of tiny card operations

The standard model's genboxes tail performs sigmoid/exp, reshapes and concatenations to turn the three detector heads into candidate boxes. It was implemented as many small operations with meaningful dispatch overhead. The raw-head path stops after the head convolutions, packs the outputs, and transfers them to the host. The host decodes candidates in compiled code and applies the same coordinate transforms and filtering logic.

At 320, the genboxes tail was about 229 operations and 1.133 ms of a 3.858 ms frame. Moving this tail off-card reduced a measured pipeline from 5.95 to 3.74 ms/frame. Those figures are from the earlier 320 pipeline, not an isolated m640 ablation.

The mAP metric is AP at IoU 0.5, averaged over classes with ground truth. The post-processing changes deliberately emphasize recall and ranking. Extra candidates cost host work, so the confidence floor and NMS settings were measured rather than lowered without limit.

9. Four custom Tensix kernels

The kernels target different sources of cost: one expensive nonlinear function, repeated graph boundaries, a multi-op pooling block, and layout conversions in the neck. They were implemented as custom device operations and ported to the six selected configurations, including bf16 variants for the larger graphs.

KernelOriginal workImplementationMeasured effect and precision notes
K1: Mish Repeated elementwise Mish calls after convolutions. Compute an algebraically equivalent Mish form, x − 2x / ((1 + e^x)^2 + 1). Approximate the exponential and reciprocal with hand-scheduled SFPU operations; interleave two rows to keep the instruction stream occupied. Separate kernels handle bfp8 and bf16 paths. One 25,600 × 64 Mish call: library 54.6 µs, V12 27.7 µs, V14 15.5 µs (~3.5×). The m640 graph is bf16, so it runs V34 (V14 plus round-to-nearest bf16): on a 62-core bf16 shard, 105.0 → 30.7 µs, max abs error .0101 vs fp32 Mish, PCC ≥ 0.99992. These are per-call benchmarks, not a 3.5× whole-model speed-up.
K2: Mish + residual add At 23 ResBlock tails, compute Mish, store/reload, then add the skip tensor. Load the operands into the on-core dataflow, run Mish on the SFPU, then issue the FPU add using the destination registers; write the final result once. Removes 23 graph ops/frame and an intermediate write/read. At bfp8, it also avoids an intermediate Mish rounding before the add; m640's activations are bf16, so the key m640 win is the fused op/dataflow rather than claiming that bfp8-specific rounding benefit.
K3: SPP max-pool Three spatial max-pool windows (5, 9, 13) and their intermediate graph operations. Use the identity that a larger max window can be built from cascaded smaller max windows. A multi-core operation gathers sharded data and computes the required max values in a controlled layout. In the isolated 320 benchmark, 136.8 → 16.7 µs (8.2×); the SPP output is bit-exact. The general kernel replaces a 12-op block with one operation.
K4: upsample + concat Two neck paths with upsample, layout changes and concatenation before the following convolution. Use the NoC/data-movement cores to gather source tiles, repeat rows for 2× upsampling and write directly into the next convolution's sharded layout. About nine operations become one per chain; byte-exact. Isolated traced saving was about 83 µs across the two chains.

Combined kernel result

On m640, the custom stack reduced COCO1k time from 2.416 ms/photo in the base folder to 1.672 ms/photo with kernels plus box-step v2. The comparison combines several device kernels and the host-only v2 change, so it is not a clean attribution of all 30.8% to one kernel. The paired COCO1k result was .6392 → .6439 mAP@50; the measured difference is small relative to dataset variation, not evidence that the kernels alone improve accuracy.

10. Runtime and I/O changes on the card

Remove work that does not change the tensor values

  • Disable a halo-output reallocation that copied convolution outputs into fresh buffers; 20 Move operations disappeared in the tested graph.
  • Skip an unnecessary input Move.
  • Skip three add(x, 0) operations that only converted dtype where the following operation accepted the tensor directly.
  • Copy output to a DRAM buffer and read it on command queue 1 with events, allowing the download for one pass to overlap the next trace where dependencies allow.

The combined config/I/O patch reduced the measured graph from 401 to 379 operations, cut the inter-frame idle gap from 114 to 4 µs, and saved roughly 0.12–0.23 ms/frame in the original ablation. The exact gain varies with graph and batch mode; the operation count is not a claim that every removed operation saves the same time.

Why reducing operation count matters

The 320 graph was estimated at roughly 10 GMAC, below a millisecond of idealized arithmetic on the card. In practice, many small graph operations and dispatch gaps dominated. Therefore the design prioritized fewer launches, fused dataflow, sharding-aware writes and overlapping transfers over simply increasing arithmetic precision or peak compute.

Why the team selected m640

  • m512 wins on raw throughput, but its practice mAP is only .0317 above the .447 floor. The team chose not to risk that narrow margin for the additional speed.
  • r320 has similar practice mAP to m640, but is slower because four inputs no longer share one model pass.
  • r384 and r512 trade throughput for more spatial detail and higher mAP. They are valid points on the curve, but do not match the selected speed objective.
  • r640 is the most accurate on practice, but the COCO1k result is almost the same as r512 while taking substantially longer.
Final choice: m640 is not the fastest or most accurate model in isolation. It is the selected operating point on the measured Pareto frontier: 2.106 ms/photo and .5586 practice mAP@50 with the custom kernels and box-step v2 enabled.

Fair-comparison caveat: the alternative-model card times exclude parts of the harness (including image decode and box processing), so they are lower bounds, not comparable end-to-end latency claims. The CPU-reference mAP figures and the YOLOv4 final pipeline figures also come from distinct evaluation paths. We used the alternatives to decide whether changing model families was promising, not to claim a precise head-to-head runtime win from incomplete runs.

Measurement note: Results are tied to the stated evaluation set, configuration and timing protocol. Per-kernel microbenchmarks, early pipeline ablations, practice-set end-to-end results, COCO1k comparisons and stress tests answer different questions; they should not be combined into a single additive speed-up calculation.
